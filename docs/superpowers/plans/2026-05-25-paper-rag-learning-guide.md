# Paper RAG 学习与演进 TODO 清单

> **面向学习者：** 这份文档是一个可执行清单。它的目标不是一次性讲完所有概念，而是带你按顺序把“检索质量 + 评估体系 + 拓展实验”真正做出来。  
> **目标：** 在保留当前 `Streamlit` 上传/问答主流程的前提下，补齐 RAG 的关键能力，并形成可回归、可验证、可持续优化的闭环。  
> **架构：** 维持“前端入口 + 入库管线 + 检索/生成管线 + 离线评估”四层结构；先提升检索质量，再建立评估标准，最后再做 GraphRAG / Agentic RAG 这类拓展。  
> **技术栈：** Python、Streamlit、LangChain、Chroma、BM25、Ollama、PyTorch、Hugging Face、离线评估脚本、Markdown/CSV/JSON。

---

## 0. 使用方式

1. 按顺序完成任务。
2. 每个任务尽量保持“一个目标、一个结果”。
3. 所有优化都要先回到基线再比较。
4. 如果某个任务完成后没有可量化变化，就先停下来，不要急着继续加功能。

## 3. 基准集任务

### 任务 1：建立 20 条人工标注基准样本

**目的：** 先定义“什么叫答得对”，后面的优化才有标准。  
**建议字段：**

| 字段 | 含义 |
|---|---|
| `id` | 样本编号 |
| `question` | 问题 |
| `gold_answer` | 人工标准答案 |
| `gold_sources` | 相关文件和页码 |
| `gold_evidence` | 关键证据片段 |
| `task_type` | 对比、定义、方法、实验、细节、追问 |
| `difficulty` | 简单 / 中等 / 困难 |
| `notes` | 标注备注 |

**建议覆盖的问题类型：**

| 类型 | 示例 | 为什么要有 |
|---|---|---|
| 定义类 | “什么是 Transformer？” | 测试基础回答稳定性 |
| 对比类 | “BERT 和 ViT 有什么区别？” | 测试多证据对比能力 |
| 方法类 | “论文用了什么方法？” | 测试方法描述准确性 |
| 细节类 | “实验设置是什么？” | 测试局部证据检索能力 |
| 追问类 | “那它为什么这么做？” | 测试多轮上下文改写 |
| 证据类 | “这句话在原文哪一页？” | 测试来源定位能力 |

**建议样本格式：**

```json
{
  "id": "q001",
  "question": "BERT 和 ViT 在 Transformer 使用上有什么不同？",
  "gold_answer": "BERT 使用双向 Transformer，ViT 片段中未明确说明方向性。",
  "gold_sources": [
    {"file": "bert.pdf", "page": 3},
    {"file": "vit.pdf", "page": 5}
  ],
  "gold_evidence": [
    "BERT 使用 bidirectional Transformer",
    "ViT 片段未提及 Transformer 方向性"
  ],
  "task_type": "compare",
  "difficulty": "medium",
  "notes": "用于测试对比型问答与证据对齐"
}
```

**验收：**

- [ ] 有 20 条以上可运行样本
- [ ] 每条样本都有答案和证据页码
- [ ] 每条样本都能在当前系统里跑一遍

## 5. 检索质量增强任务

### 任务 3：实现第一个 rerank

**目的：** 先召回，再重排，让最相关的证据排到前面。  
**为什么先做这个：** 这是最直接影响回答质量的模块，也最适合先验证效果。

**建议优先级：**

| 方案 | 复杂度 | 适合度 |
|---|---|---|
| API rerank | 低 | 快速验证，但依赖外部服务 |
| 本地轻量 reranker | 中 | 推荐先做 |
| 本地 cross-encoder | 中高 | 学习价值高，但实现成本更高 |

**建议实现路径：**

1. 先保留当前混合检索召回。
2. 对召回结果按问题与片段的相关性重排。
3. 只把重排后的前 N 个片段送入生成模型。

**验收：**

- [ ] 能输出 rerank 前后的顺序差异
- [ ] 关键样本的答案更贴近基准答案
- [ ] 检索结果噪声减少

### 任务 4：实现 query expansion / multi-query

**目的：** 解决“问法不同导致搜不到”的问题。  
**关键说明：** 论文问答里，中英文、缩写、同义表达非常多，单一 query 很容易漏召回。

**建议做法：**

- 原问题不变
- 生成 2-4 个改写版本
- 每个版本分别检索
- 合并结果后再重排

**验收：**

- [ ] 能看到多个 query 的检索结果
- [ ] 对缩写、同义表达、中文英文混问更稳

### 任务 5：实现 context compression

**目的：** 只把真正支撑答案的句子送给 LLM。  
**关键说明：** 这是减少 prompt 噪声和降低生成成本的关键手段。

**建议做法：**

- 先得到 chunk 级候选
- 再提取每个 chunk 里最相关的句子
- 最后把精简后的证据拼进 prompt

**验收：**

- [ ] prompt 更短
- [ ] 生成回答更集中
- [ ] 长上下文时不容易跑偏

### 任务 6：实现 parent document retrieval

**目的：** chunk 命中后回溯整页或整段上下文。  
**关键说明：** 论文 PDF 场景里，chunk 太碎会导致答案缺上下文，父文档回溯能补这个洞。

**建议做法：**

- child chunk 负责召回
- parent page / parent section 负责生成
- 前端仍然显示页码和来源

**验收：**

- [ ] 命中的证据更完整
- [ ] 长文档问题更稳
- [ ] 页码展示仍然清晰

## 6. 评估体系任务

### 任务 7：建立离线自动评估脚本

**目的：** 让每次改动都能自动比较，不靠主观感觉。  
**为什么必须做：** 没有评估，优化很容易变成“看起来复杂，但没有真的更好”。

**建议评估两层：**

| 层级 | 指标 | 作用 |
|---|---|---|
| 检索层 | Recall@k、MRR、nDCG | 看证据找得准不准 |
| 生成层 | 答案一致性、引用命中率、人工打分 | 看回答是否可信 |

**建议输出：**

- `results.csv`
- `summary.json`
- 失败样本列表
- Markdown 报告

**验收：**

- [ ] 一条命令就能跑评估
- [ ] 结果可对比、可复现
- [ ] 能发现版本回归

### 任务 8：把失败样本回流到基准集

**目的：** 把前端里答错的问题沉淀成新的标注样本。  
**关键说明：** 这是把“用户体验问题”变成“下一轮优化输入”的最实用方法。

**建议做法：**

- 前端中记录答错或不满意的问题
- 导出到 `benchmarks/labels/`
- 定期补到基准集里

**验收：**

- [ ] 有失败样本池
- [ ] 能持续扩充基准集
- [ ] 基准集能反映真实使用问题

## 8. 拓展实验任务

### 任务 10：预留 GraphRAG / Agentic RAG 接口

**目的：** 在主线稳定后，方便继续做更重的实验。  
**关键说明：** 这两个方向复杂度高，应该作为拓展，不要提前侵入主流程。

**建议先预留什么：**

- 图谱数据结构接口
- 工具调用接口
- 检索失败重试入口

**验收：**

- [ ] 主流程不受影响
- [ ] 拓展模块能独立开关
- [ ] 失败时不破坏现有问答

## 9. 与 Streamlit 前端的边界

`Streamlit` 继续只负责业务入口，不做评估主界面。

| 功能 | 处理方式 |
|---|---|
| 上传 PDF | 保留 |
| 一键入库 | 保留 |
| 问答 | 保留 |
| 来源展示 | 保留 |
| 评估结果展示 | 只放轻量入口 |
| 错例导出 | 可后续加轻功能 |

**说明：**  
前端负责“用户体验”，离线脚本负责“质量验证”。两者保持分离，项目会更清楚。

## 11. 最小落地顺序

如果你现在就要开始做，我建议按这个顺序推进：

1. [ ] 写 20 条基准样本
2. [ ] 跑当前版本，保存基线
3. [ ] 做第一个 rerank
4. [ ] 复跑评估，看变化
5. [ ] 做 query expansion
6. [ ] 做 context compression
7. [ ] 做 parent document retrieval
8. [ ] 加结构化日志
9. [ ] 再考虑 GraphRAG / Agentic RAG

**为什么这个顺序合适：**

- 先有标准，不会盲改。
- 先做最影响质量的模块。
- 再做更重的优化，避免项目变复杂却看不出收益。

## 12. 验收标准总表

| 目标 | 验收方式 |
|---|---|
| 检索质量提升 | Recall@k / MRR 上升，失败样本减少 |
| 回答质量提升 | 人工抽查中证据更准、幻觉更少 |
| 评估闭环建立 | 改动后能自动出报告 |
| 前端不臃肿 | `Streamlit` 仍然只做上传和问答主流程 |
| 拓展能力保留 | GraphRAG / Agentic RAG 可独立接入 |
